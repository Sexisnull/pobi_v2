Deadend CLI — 流程架构图解

一个“完全本地运行、模型无关”的自主 Web 应用渗透测试智能体。本页面用一组流程图拆解它的 系统分层、端到端请求流、ADaPT 反馈循环，以及子智能体与工具的拆解。 先别急着记住细节——试着在每张图前先想一个问题：“这一步为什么需要存在？”

引导思考： 如果让你从零设计一个“会自己黑网站”的 AI，你会先搭哪一层？ 是先把 UI 做漂亮，还是先想清楚“AI 怎么调用工具、工具怎么隔离、结果怎么回传”？ Deadend 的答案藏在下图的分层里。

① 系统架构（分层与依赖）

整条链路是 前端（TS）→ 进程间 JSON-RPC（stdio）→ Python 守护进程 三层， 再向下挂接沙箱、向量库与 LLM。注意：CLI 本身不懂渗透，它只是把意图翻译成 RPC 调用。

② 端到端请求流（一次 deadend --target … 发生了什么）

从敲下命令到屏幕上出现实时进度，其实是 8 步 RPC 往返。重点看 run_agent_recursive： 它内部串起了“侦察 → 利用”两个阶段，并且每个阶段都通过 EventBus 把事件推给 UI。 

flowchart TD
  Start(["用户在终端输入 deadend --target URL --prompt"]) --> L1
  L1["server-launcher 启动 Python 守护进程"] --> L2
  L2["init_all : Docker→Config→RAG→ModelRegistry→Shell沙箱→Playwright"] --> L3
  L3["instantiate_agent(target) 生成 agent_id + 沙箱 + RAG 会话"] --> L4
  L4{"是否先建索引?"} -->|"是"| L5["embed_target : crawl_target + embed_target → RAG (init→done)"]
  L4 -->|"否"| L6
  L5 --> L6["run_agent_recursive(agent_id, prompt)"]
  L6 --> L7["threat_model_stream : execute_supervisor → recon_report.md"]
  L7 --> L8["start_testing_stream : ADaPT 利用循环 → exploit_report.md"]
  L8 --> L9["subscribe_events (并行) : EventBus 实时推送 UI"]
  L8 --> L10["get_agent_tasks : 轮询 TaskRegistry 任务树"]
  L9 --> End(["UI 展示进度 / 报告"])
  L10 --> End
  L8 -.->|"ValidationStopEvent"| L9

  subgraph APPROVE["审批模式 (hacker mode)"]
    P1["工具调用前发出 approval 事件"] --> P2["UI 调用 approve(request_id)"]
    P2 --> P3["event_bus.respond_to_approval → 工具执行"]
  end
  L8 -.可能需要人工确认.-> P1

③ ADaPT 反馈循环（项目的核心创新）

这是 Deadend 区别于“一次性调用工具链”的关键：每轮执行后，智能体给结果打一个 信心分 0–1.0，再据此决定下一步动作。信心不是装饰——它是状态机的转移条件。 

flowchart TD
  Root["根任务 (TaskNode) : 目标 = 找到漏洞 / 拿到 flag"] --> Sup["Planner / Supervisor 分解出子任务"]
  Sup --> Loop{"ADaPTAgent.run(task, context)"}

  Loop --> Exec["子智能体执行工具
(Requester / Python / Shell)"]
  Exec --> Res["得到 ResultEvent :
context + confidence_score"]
  Res --> Gate["ValidationGate 检查
(flag 正则 / judge LLM)"]

  Gate -->|"命中 → stop:true"| Solved(["goal_achieved=true
生成 exploit_report.md 并退出"])
  Gate -->|"未命中"| Decide{"信心分?"}

  Decide -->|"< 0.2 失败"| Fail["FAIL : 放弃该分支
记录失败原因"]
  Decide -->|"0.2–0.6 扩张"| Expand["EXPAND : 拓宽搜索面
并行派生更多子任务"]
  Decide -->|"0.6–0.8 精炼"| Refine["REFINE : 同方向调整
生成自定义 payload 再试"]
  Decide -->|"> 0.8 验证"| Validate["VALIDATE : 确认并固化证据
(proof)"]
  Decide -->|"= 上限深度"| Maxd["max_depth 兜底 : 收尾报告"]

  Fail --> Feedback
  Expand --> Feedback
  Refine --> Feedback
  Validate --> Feedback
  Maxd --> Solved

  Feedback["反馈驱动 : 把 context / result 写回 ContextEngine
(AVFS 记忆 + RAG)"] --> Loop

  Refine -.->|"标准工具失败"| Custom["生成自定义 Python 脚本
(Pyodide/WASM 或 Shell 沙箱)
观察响应 → 迭代"]
  Custom --> Exec
自问自答： 为什么“盲注 SQLi”这类题，传统静态工具得 0%， 而 Deadend 能到 33%？关键在于 REFINE 分支里的 “生成自定义脚本 + 观察响应 + 再精炼” 闭环——它把“工具不会”转化成了“写代码去试”。

④ 两阶段流程：侦察 → 利用

宏观上，整个评估是 先侦察（recon / threat model）后利用（exploit） 的两段式。 侦察产物（威胁模型 + recon_report）会被喂进利用阶段的上下文，而不是各跑各的。 

flowchart LR
  subgraph RECON["阶段一 · 侦察"]
    R1["crawl_target 爬取目标"] --> R2["embed_target 入库 RAG"]
    R2 --> R3["execute_supervisor 建威胁模型"]
    R3 --> R4["ReporterAgent → recon_report.md"]
  end

  subgraph EXPLOIT["阶段二 · 利用"]
    X1["读取 recon_report 作为 exploit_context"] --> X2["ADaPTAgent 信心反馈循环"]
    X2 --> X3["逐漏洞利用 / 自定义 payload"]
    X3 --> X4["ValidationGate 判定"]
    X4 --> X5["ReporterAgent → exploit_report.md"]
  end

  R4 --> X1
  X5 --> Done(["评估结束 : 输出两份报告 + 任务树"])

⑤ 子智能体与工具拆解

available_agents 把不同“能力”拆分给专门的子智能体，每个都绑定一类工具。 关键设计：危险操作（命令执行、浏览器）一律跑在隔离沙箱里。
