① 目标定位：你打开这份指南要做什么

这份指南服务于一个目标——在 fork（二次开发）deadend-cli 的基础上做完善。它不要求你从 main 通读到最后一个文件，而是帮你先摸清在哪下刀。

Deadend CLI 是一个自主 Web 应用渗透测试 agent，核心特征是：

  • 反馈驱动迭代（ADaPT）：标准工具失败时，自动生成自定义 Python payload、观察响应、再迭代，直到突破。
  • 信心驱动决策：每轮给任务打 0–1.0 信心分，据此 fail(<0.2) / expand(0.2–0.6) / refine(0.6–0.8) / validate(>0.8)。
  • 两阶段：先 recon（侦察+威胁建模+RAG 入库），后 exploit（吃上下文跑 ADaPT 循环）。
  • 完全本地 / 模型无关：LiteLLM 抽象多供应商，零云端依赖。
  • 成绩：XBOW 黑盒套件 78%（盲注 SQLi 从 0% 做到 33%）。
读源码前先能不依赖代码、用自己的话讲出上面五点。讲不通就先回看架构图（见 deadend_cli_architecture.html）。

② 环境搭建（第 0 步：仓库还没 clone）

当前工作目录里只有架构图，仓库源码未拉取。先把它拿下来并建立开发环境：

  1. Clone：git clone https://github.com/straylabs-ai/deadend-cli（注意上游 org 实际为 xoxruns，以仓库页为准）。
  2. Python 环境：需 Python 3.11+ 与 uv >= 0.5.30。在项目根执行 uv sync 安装 workspace 全部依赖。
  3. Playwright：playwright install（Requester 工具依赖浏览器自动化）。
  4. Docker：必须。Shell 工具在 Docker/Kali 沙箱里隔离执行。deadend-cli init 会拉起 pgvector 与 Docker 前置。
  5. 配置模型：~/.deadend/config.json
  6. 冒烟测试：跑通 deadend-cli init，再用 deadend-cli eval-agent 跑通 1 道题。能跑通 1 题 = 环境 OK。
⚠️ 仅在你有权限的目标上测试（自有靶场 / 授权渗透 / CTF）。未授权扫描违法。仓库 DISCLAIMER 已明确此点。

③ 扩展点地图（fork 后"在哪下刀"）

架构刻意模块化，扩展缝很清晰。下列每一格 = 一个二次开发入口：

子智能体 / 工具

加新角色或工具

在 agents/factory.py 注册，并加入 deadend_agent.py 的 available_agents 字典。能力边界由 deadend_prompts/ 的 system prompt + 授权工具决定。

验证策略

加新停机条件

扩展 config/validation.default.yaml 的 strategies，并在 validation 系统实现对应 strategy 类（在 flag/judge 之外加你的，如"多证据投票 judge"）。

RPC / CLI

加新命令

jsonrpc_server.py 暴露新方法，前端 cli/deadend/src/ 调用。README roadmap 的 plan mode 正是 RPC+UI 扩展点。

模型层

换 / 加供应商

LiteLLM 已抽象，基本只改配置。想换本地 Llama/Qwen 也走这里——这是 roadmap "Open-Source Models" 目标。

策略旋钮

调"自主性"

core_agent/core_agent.py 的信心带 0.2/0.6/0.8 与 TaskNode 递归深度，是皇冠上的旋钮——决定 agent 多激进。

工作流

预设 / 回放

README roadmap 的 Preset configuration workflows（API / web / auth bypass）与 Workflow automation（save/replay）明确标 "In Progress"，是现成缺口。

⑤ eval 验证流程（改完怎么知道没改坏）

这是二次开发最值钱的部分——评分体系已搭好，直接复用当回归测试：

  1. deadend-eval + XBOW 套件：deadend-cli eval-agent --provider <p> --model-name <m> 跑 104 题黑盒套件。改一处 → 跑 eval → 看总分 / 盲注成功率变化。
  2. Arize Phoenix trace：开 Phoenix 看每次迭代 span，定位决策异常。
  3. 单题 trace：挑一个 CTF 题，改前改后各跑一遍对比。
  4. 改阈值验证：调 0.2/0.6/0.8 看行为变化——能预测并验证行为改变 = 真读懂。
基准参考（README）：XBOW 验证套件 78%（76/98），含盲注 SQLi 33%。强项 XSS 91% / 业务逻辑 86% / SQLi 83% / IDOR 80%。你的改动应以"不掉分、特定类目加分"为目标。

⑥ monorepo 结构提醒

pyproject.toml 里 [tool.uv.workspace] 的 members：

成员包职责
deadend_agent核心 agent 逻辑（ADaPT 循环、supervisor、子智能体、工具）。
deadend_prompts各角色 system prompt 模板（.jinja2）——改行为先来这。
deadend_eval评测 harness（XBOW 套件驱动）。
simple-python-interpreter-sandboxPython 沙箱客户端（WASM/Pyodide）。
加新能力时：要么在现有 package 内加模块，要么新开一个 workspace package 并在 pyproject.toml 的 [tool.uv.workspace].members 登记。先理解这层，后面加代码才不会放错地方。

⑦ 学习即开发：前两步（避开"没跑通就大改"）

二次开发最危险的误区是还没在本地跑通就动手大改。你的第一个里程碑应是："让它能在我机器上跑起来、并跑通 1 题 eval"——这本身就是一次有价值的二次开发。

  1. 环境就位：clone → uv sync → playwright install + Docker → init → 跑通 eval-agent 的 1 题。
  2. 最小扩展动手：挑最窄的缝——给 validation 加一个自定义 strategy，或给 factory 加一个只读 router 子智能体。改 → 跑 eval → 看分数。
  3. 啃 Roadmap 缺口：推荐先实现 plan mode（执行前预览策略）——最直观、最易验证、且 README 明说在做。

⑧ 合规与风险

⚠️ 仅用于授权安全测试。未授权测试违法，用户须自行确保合规与授权。仓库 DISCLAIMER 已明确。

二次开发时尤其注意：

  • 工具在 Docker/Kali 与 WASM 沙箱中隔离执行——不要为了"方便"关掉沙箱，那是安全设计的核心。
  • ValidationGate 的停机逻辑是"别越界"的保险——自定义 strategy 时别让它无限循环攻击。
  • "fully local / zero data exfiltration" 是设计承诺，二次开发应保持。
